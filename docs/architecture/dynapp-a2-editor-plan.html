Architecture plan

Dissolved A2 Code for the DynApp app store

Dissolve the current A2server boundary into two places: trusted shell capabilities and richer A2 Code DynApp content. Users install DynApp once and can modify any app without a separate backend process or server product.

Target: DynApp shell package Editor: A2 Code DynApp Server boundary: dissolved Package rules: dynapp-package-spec.md

Product Goal

The app store selling point is not just installing apps. It is that installed apps are easy to inspect, modify, run, test, and publish back from the same desktop shell.

Install once
DynApp Shell Trusted install, app store, sandbox, updates, signed payloads.
→
A2 Code DynApp The editor UI and modification workflow, shipped as bundled content.
→
Shell Capabilities Typed privileged APIs for files, processes, PTYs, providers, git, and packaging.

Boundary Decision

The old server should not remain a bundled service. Its responsibilities should be rehomed: product logic and pure orchestration in content; authority, secrets, process control, durability, and trust enforcement in the shell package.

Capability Owner Why
Editor UI, app-store modification flows, thread presentation A2 Code content Fast to iterate, hot-updatable, product-specific, low authority.
Provider subprocesses, PTYs, filesystem writes, git mutations Shell capabilities Needs durable ownership, OS integration, cancellation, logs, and security policy.
App build/package/sign/publish operations Shell capabilities Touches trusted signing keys and controls what becomes installable.
Pure reducers, command composition, non-secret preferences A2 Code content Can survive as browser code and can be tested without privileged APIs.
Contracts, schemas, event formats, project references Shared contracts Both sides need stable typed boundaries and migration compatibility.

Add To The Shell

The reduced shell needs typed capabilities, not a bundled A2server and not an app-specific privileged namespace. Any DynApp can request capabilities in its manifest; the shell displays their danger level at install/update time and enforces them at runtime.

Trusted base

General capability registry

  • Add typed shell capabilities any DynApp can request through app.json.
  • Expose project, file, process, provider, terminal, git, and packaging APIs as normal shell capability groups.
  • Grant capabilities only after install/update review by the user.
  • Advertise capabilities and versions so content can feature-gate safely.
  • Reject unknown, undeclared, or ungranted operations at the shell boundary.

Streaming process and PTY APIs

  • Replace command-only fs.exec usage with process handles.
  • Stream stdout, stderr, lifecycle events, and exit codes.
  • Support stdin writes, cancellation, timeouts, and backpressure.
  • Support PTY sessions for terminals and provider CLIs that expect TTY behavior.
  • Persist process logs for diagnostics and agent replay.

Project filesystem authority

  • Explicitly grant project roots.
  • Normalize paths and prevent root escape.
  • Provide patch/apply operations, not only raw writes.
  • Emit file-watch events for editor sync.

Git and source control bridge

  • Run git mutations under shell authority.
  • Support branch/worktree operations.
  • Surface source-control provider auth state.
  • Keep secrets outside content.

DynApp build and publish APIs

  • Build app content with declared commands.
  • Package signed payloads.
  • Diff permission changes.
  • Submit app updates to the registry.

Permission and trust enforcement

  • Assign every shell capability a danger level and plain-language explanation.
  • Show requested permissions and changed permissions during install and update.
  • Require extra confirmation for very-high-danger capabilities such as process handles and PTY access.
  • Record audit logs for filesystem writes, shell commands, packaging, and publish operations.
  • Let A2 Code request powerful editor permissions through the same manifest model as every other DynApp.

Permission danger levels

Level Examples Install wording
Low App metadata, UI preferences, notifications, opening external links This app can change its own experience but cannot inspect your files.
Medium Read files in selected project roots, file watchers, clipboard read This app can read selected local content.
High Write files, apply patches, mutate git state, connect to remote targets This app can change project content or send work to another machine.
Very high Execute commands, open PTYs, hold process handles, package/sign/publish apps, access secrets This app can run code on this machine or publish signed artifacts.

Manifest declaration

{
  "permissions": [
    { "capability": "files.read", "scope": "selectedProjectRoots" },
    { "capability": "files.write", "scope": "selectedProjectRoots" },
    { "capability": "process.spawn", "scope": "projectCommands" },
    { "capability": "pty.open", "scope": "projectTerminals" }
  ]
}

The app declares what it needs. The shell owns the registry, maps each capability to a danger level, shows the combined install/update review, and denies undeclared calls even if content tries them.

Remote execution adapters

  • Keep local editing zero-install beyond DynApp itself.
  • Add optional remote capability providers for Windows, Linux, and cloud builds.
  • Use the same capability interface across local shell APIs and remote adapters.
  • Represent remote machines as build/test targets, not required setup.
  • Keep remote transport hidden behind the same typed shell capability groups.

Land In The A2 Code DynApp

A2 Code content should own the product experience. It should ask the shell for capabilities, not directly control the operating system.

Hot-updatable editor

App-store modification UX

  • Create new DynApps by copying templates/dynapp-boilerplate/.
  • Open installed app source.
  • Fork or clone an app from the registry.
  • Show app metadata, permissions, scripts, and version.
  • Guide users through modify, preview, test, package, and submit.

Spec-aware editing

  • Load dynapp-package-spec.md as the editing rulebook for DynApp projects.
  • Keep app.json, permissions, license, source layout, and docs aligned with the spec.
  • Warn when an edit lowers shareability or modifiability score before package or publish.
  • Generate repair tasks for missing required files, broad permissions, or undocumented behavior.

Editor and agent workflow

  • Prompt composer and thread UI.
  • Pure orchestration reducers and command planning.
  • Thread/event projections that can be reconstructed from shell event logs.
  • Diff review and accept/reject controls.
  • Task plans and agent progress.
  • Artifact and transcript views.

Capability-aware commands

  • Build command payloads from typed shell capabilities.
  • Gate UI by shell capability version and permissions.
  • Show clear errors for unsupported targets.
  • Avoid exposing raw command strings as the primary API.

Environment and target selection

  • Default to local DynApp shell capabilities.
  • Offer optional Windows/Linux/cloud targets for build and test.
  • Scope projects, threads, terminals, and previews by execution target.
  • Make “where actions run” visible in every destructive or expensive workflow.

Local browser storage

  • Cache presentation state in IndexedDB or local storage.
  • Store non-secret editor preferences.
  • Hydrate thread/project snapshots while shell capabilities initialize.
  • Never store provider tokens, signing keys, or privileged credentials in content.

Proposed Capability API

The boundary should be typed, narrow, and workflow-oriented. Raw filesystem and raw shell execution should be implementation details behind higher-level methods. 

window.appShell = {
  capabilities: {
    list(),
    getGrantState(),
    request(),
    subscribe()
  },
  files: {
    openPath(path),
    read(projectId, path),
    write(projectId, path, contents),
    applyPatch(projectId, patch),
    watch(projectId)
  },
  processes: {
    spawn(command, options),
    write(processId, data),
    signal(processId, signal),
    subscribe(processId)
  },
  terminals: {
    open(projectId, cwd),
    write(sessionId, data),
    resize(sessionId, size),
    close(sessionId)
  },
  dynapp: {
    inspect(appId),
    livePreview(appId),
    build(appId),
    package(appId),
    submit(appId)
  }
}

// Every method is available only when the DynApp declares the matching
// capability and the user grants it during install or update.

Migration Plan

Dissolve A2server incrementally by moving each responsibility to either shell capabilities or A2 Code content. Avoid creating a new permanent service boundary.

Inventory A2server responsibilities

Classify each current server module as shell authority, content logic, shared contract, or obsolete transport glue. This is the decision log that prevents a server-shaped service from reappearing under a new name.

Define the shell capability contracts

Create schemas for shell-hosted capabilities, event logs, process handles, PTY sessions, project operations, provider turns, git mutations, and DynApp packaging.

Build shell capability implementations

Implement filesystem authority, process/PTY streaming, provider subprocess control, git/source-control mutations, app packaging, signing, and durable event logs directly in the DynApp shell.

Move pure runtime logic into content

Port command composition, orchestration reducers, thread projections, app-store modification flows, diff review, and non-secret settings into the A2 Code DynApp.

Retire HTTP/WebSocket server glue locally

Replace local server RPC with direct shell capability calls. Keep remote targets behind adapters that expose the same capability contract to content.

Add optional remote targets

Let advanced users connect Windows/Linux/cloud capability providers for testing and builds, while keeping local modification available immediately after installing DynApp.

Risks And Rules

The split only helps if content cannot become an unbounded privileged script runner.

Do not expose raw exec as the core editor API

Raw execution is useful as an escape hatch for trusted editor workflows, but normal app modification should go through typed project, agent, build, and package APIs.

Shell owns durability for active work

Agent turns, provider processes, PTYs, event logs, and packaging jobs must survive content reloads. Content can render and coordinate, but shell services own active host-side lifetimes.

Version compatibility

  • Content checks shell capabilities at startup.
  • Shell rejects unknown privileged operations.
  • Feature flags are capability-based, not version-string based.

Security posture

  • All DynApps use the same manifest permission model.
  • A2 Code is powerful because it asks for more capabilities, not because it gets special shell access.
  • Signing keys and provider secrets stay in shell storage.

User promise

  • No separate local backend install.
  • Modify works offline for local projects.
  • Remote machines are optional accelerators.
