Architecture plan

A2 Code as a DynApp

Dissolve A2server into generic Shell capabilities and A2 Code content. Start with the locally connected Shell over IPC; keep the contract transport-independent so remote DynApps can be added later without an A2-specific protocol.

Target: DynApp shell package Editor: A2 Code DynApp Server boundary: dissolved Package rules: dynapp-package-spec.md

Product Goal

The app store selling point is not just installing apps. It is that installed apps are easy to inspect, modify, run, test, and publish back from the same desktop shell.

Install once
A2 Code DynApp Editor UI, agent orchestration, git workflows, package rules, and app-making experience.
→
Generic appShell contract Typed APIs over local IPC in the first migration stage.
→
Local DynApp Shell Permission enforcement and generic files, processes, credentials, networking, and app-management capabilities.

Boundary Decision

The old server should not remain a bundled service. Its responsibilities should be rehomed: product logic and pure orchestration in content; authority, secrets, process control, durability, and trust enforcement in the shell package.

Capability Owner Why
Editor UI, app-store modification flows, thread presentation A2 Code content Fast to iterate, hot-updatable, product-specific, low authority.
Filesystem access, process sessions, PTYs, and credentials Shell capabilities Needs durable ownership, OS integration, cancellation, logs, and security policy.
Agent protocols, git workflows, build/package/publish orchestration A2 Code content Product logic composes existing generic process, filesystem, archive, network, and app APIs.
Pure reducers, command composition, non-secret preferences A2 Code content Can survive as browser code and can be tested without privileged APIs.
Capability schemas, process events, and handles Shared contracts Both sides need stable typed boundaries and migration compatibility.

Add To The Shell

Most required authority already exists in the DynApp Shell. Reuse its schema-v2 backendPermissions, extend the existing execution grants with managed process sessions, and add secure credentials plus danger metadata.

Trusted base

Existing capability registry

  • Keep using normal backendPermissions entries with a specific user-facing reason.
  • Reuse fs.*, net.*, and apps.* instead of adding A2, git, preview, build, package, or publish namespaces.
  • Grant capabilities only after install/update review by the user.
  • Advertise capabilities and versions so content can feature-gate safely.
  • Reject unknown, undeclared, or ungranted operations at the shell boundary.

Extend execution actions with process sessions

  • Commander already uses the very-high fs.exec permission; reuse that execution grant.
  • Subtrans already receives completed stdout and stderr from fs.execFile; retain it for bounded commands.
  • Add managed pipe and PTY modes without a new permission name.
  • Stream stdout, stderr, lifecycle events, and exit codes.
  • Support stdin, resize, signals, restart, cancellation, and backpressure.
  • Return opaque handles with ownership, leases, and deterministic cleanup.
  • Keep bounded event replay so content can recover after a reload or reconnect.

Backward-compatible streaming toggle

type ExecOptions = {
  cwd?: string;
  stream?: boolean;                 // default false
  mode?: "pipes" | "pty";          // default "pipes"
  stdin?: "ignore" | "pipe";       // default "ignore"
  timeoutMs?: number | null;
  maxOutputBytes?: number;
  replayBytes?: number;
  env?: Record<string, string | null>;
  credentialRefs?: Record<string, string>;
  cols?: number;
  rows?: number;
  lifecycle?: "window" | "app";    // default "window"
};

exec(command, cwd?: string): Promise<ExecResult>;
exec(command, options?: ExecOptions): Promise<ExecResult | ProcessHandle>;

execFile(file, args?, cwd?: string): Promise<ExecResult>;
execFile(file, args?, options?: ExecOptions): Promise<ExecResult | ProcessHandle>;
  • With no options object, or with stream: false, preserve the current collected { code, stdout, stderr } behavior.
  • With stream: true, return an opaque { processId } handle immediately and deliver sequence-numbered events through appShell.process.
  • Prefer execFile for A2 Code agent servers so executable and arguments remain structured and do not pass through a command shell.
  • PTY mode merges output by design; pipe mode preserves separate stdout and stderr events. Both modes enforce bounded replay and output limits.

Reuse existing filesystem APIs

  • Select roots with dialog.pickPath.
  • Read with fs.list, fs.stat, and fs.readText.
  • Write with fs.writeText, fs.copy, and related APIs.
  • Use fs.watch and search.files for editor sync.

Compose workflows in content

  • Run git and declared build tools through fs.execFile.
  • Parse git output and own branch/worktree UX in A2 Code.
  • Apply patches in content, then write accepted file results through the Shell.
  • Keep manifest validation, scoring, and fork tracking entirely in content.

Reuse package and app APIs

  • Build through fs.execFile or managed fs.exec.
  • Package with fs.pack.
  • Publish over net.protocol.https.
  • Inspect, install, and launch with the existing apps.* permissions.

New: secrets.manage

  • Add secrets.manage to the generic Shell permission registry.
  • Store credentials in app-scoped Shell secure storage.
  • Create, replace, delete, and select secrets through Shell-owned UI.
  • Pass credential references to approved process or network operations.
  • Do not expose a generic secret-read API to content.

Permission naming policy

  • Keep all existing schema-v2 names as stable compatibility identifiers; do not rename permissions in place.
  • Define new permissions as lower-camel domain.action names. Use deeper qualifiers only for a coherent family such as net.protocol.https.
  • Replace the flat allow-list internally with permission descriptors containing domain, title, danger level, explanation, and supported runtimes; derive the allow-list and install UI from those descriptors.
  • Treat globalShortcut, externalOpen.files, file.pathForFile, dialog.message, and execution under fs.* as legacy naming exceptions, not patterns for new names.
  • If cleanup becomes worthwhile, introduce canonical names and aliases only in a future manifest schema version; old and new names must resolve to one grant and one danger record.

Permission and trust enforcement

  • Assign every shell capability a danger level and plain-language explanation.
  • Show requested permissions and changed permissions during install and update.
  • Require extra confirmation for very-high-danger capabilities such as process handles and PTY access.
  • Record audit logs for filesystem writes, shell commands, packaging, and publish operations.
  • Let A2 Code request powerful editor permissions through the same manifest model as every other DynApp.

Permission danger levels

Level Examples Install wording
Low App metadata, UI preferences, notifications, opening external links This app can change its own experience but cannot inspect your files.
Medium Read files in selected project roots, file watchers, clipboard read This app can read selected local content.
High Write, copy, remove, or package files; install applications This app can change files or installed applications.
Very high Execute commands, hold process or PTY handles, or manage credentials This app can run code or use configured credentials.

Manifest declaration

{
  "schemaVersion": 2,
  "backendPermissions": [
    {
      "permission": "fs.readText",
      "reason": "Reads project source selected by the user for editing in A2 Code."
    },
    {
      "permission": "fs.exec",
      "reason": "Runs coding agents and terminals selected by the user with streamed input and output."
    },
    {
      "permission": "secrets.manage",
      "reason": "Stores and uses credentials the user configures for coding-agent providers."
    }
  ]
}

The app declares what it needs. The shell owns the registry, maps each capability to a danger level, shows the combined install/update review, and denies undeclared calls even if content tries them.

Future stage: shell.remote.connect

  • Do not implement remote Shell support in the initial local migration.
  • Pair with another DynApp Shell and connect over authenticated WSS.
  • Return the same generic capability groups as the local Shell.
  • Bind short-lived credentials to app id, revision, device, and grants.
  • Recheck every operation against permissions granted by the remote user.
  • Do not treat ordinary net.protocol.wss as remote Shell authority.

Only one added permission for the local migration

secrets.manage. Managed process handles inherit and reuse fs.exec or fs.execFile from the action that creates them. Patch application, git workflows, previews, DynApp validation, scoring, fork notes, build composition, and thread orchestration do not need new permissions.

Land In The A2 Code DynApp

A2 Code content should own the product experience. It should ask the shell for capabilities, not directly control the operating system.

Hot-updatable editor

App-store modification UX

  • Create new DynApps by copying templates/dynapp-boilerplate/.
  • Open installed app source.
  • Fork or clone an app from the registry.
  • Show app metadata, permissions, scripts, and version.
  • Guide users through modify, preview, test, package, and submit.

Spec-aware editing

  • Load dynapp-package-spec.md as the editing rulebook for DynApp projects.
  • Keep app.json, permissions, license, source layout, and docs aligned with the spec.
  • Warn when an edit lowers shareability or modifiability score before package or publish.
  • Generate repair tasks for missing required files, broad permissions, or undocumented behavior.

Editor and agent workflow

  • Prompt composer and thread UI.
  • Pure orchestration reducers and command planning.
  • Thread/event projections that can be reconstructed from shell event logs.
  • Diff review and accept/reject controls.
  • Task plans and agent progress.
  • Artifact and transcript views.

Capability-aware commands

  • Build command payloads from typed shell capabilities.
  • Gate UI by shell capability version and permissions.
  • Show clear errors for unsupported targets.
  • Avoid exposing raw command strings as the primary API.

Local Shell binding

  • Bind A2 Code to the local DynApp Shell for the initial migration.
  • Keep projects, threads, process handles, and previews local.
  • Do not ship machine selection, pairing, or remote connection UI in this stage.
  • Keep the client contract transport-independent for the later remote stage.

Local browser storage

  • Cache presentation state in IndexedDB or local storage.
  • Store non-secret editor preferences.
  • Hydrate thread/project snapshots while shell capabilities initialize.
  • Never store provider tokens or privileged credentials in content.

Proposed Capability API

The boundary should be typed, generic, and transport-independent. A2-specific workflows are content helpers composed from these Shell primitives. 

window.appShell = {
  capabilities: {
    list(),
    getGrantState(),
    subscribe()
  },
  fs: {
    list(path),
    readText(path),
    writeText(path, contents),
    // Existing cwd strings still collect bounded output. Passing
    // { cwd, stream: true, ... } returns an opaque process handle.
    exec(command, cwdOrOptions),
    execFile(file, args, cwdOrOptions),
    packZip(paths, archive),
    watch(path)
  },
  process: {
    attach(processId),
    status(processId),
    write(processId, data),
    resize(processId, size),
    signal(processId, signal),
    close(processId),
    subscribe(processId, { afterSequence }, callback)
  },
  secrets: {
    configure(name, options),
    remove(name),
    listMetadata()
  }
}

// Every method is available only when the DynApp declares the matching
// backendPermission and the local Shell grants it. A process handle inherits
// fs.exec or fs.execFile from the action that created it.

Streaming emits started, stdout, stderr, exit, error, and replay-gap events with monotonic sequence numbers. App-lifecycle handles may survive a content reload for a bounded TTL; window-lifecycle handles are terminated when their owner closes.

Migration Plan

Dissolve A2server incrementally by moving each responsibility to either shell capabilities or A2 Code content. Avoid creating a new permanent service boundary.

Inventory A2server responsibilities

Map every current server module to existing appShell authority, secrets.manage, content logic, or obsolete transport glue. Record the result so a server-shaped service does not reappear under a new name.

Freeze the transport-independent Shell contract

Reuse schema-v2 backendPermissions. Add schemas only for secrets.manage. Extend fs.exec and fs.execFile with a backward-compatible streaming toggle, stream cursors, handle ownership, cancellation, replay, and capability discovery. Add structured permission metadata without renaming schema-v2 grants.

Implement the missing Shell primitives

Add managed pipe/PTY processes under the existing execution permissions, app-scoped credential storage and prompts, danger-level metadata, and audit records. Keep these implementations generic and available to any local DynApp.

Move pure runtime logic into content

Port command composition, orchestration reducers, thread projections, app-store modification flows, provider JSON-RPC clients, git workflows, diff review, manifest validation, scoring, and non-secret settings into the A2 Code DynApp. Persist thread and project state in content storage; keep only privileged resource lifetimes in the Shell.

Retire the local A2server transport

Replace local WebSocket RPC with direct appShell calls, verify agent process recovery across content reloads, and remove the bundled server once local files, processes, terminals, previews, builds, and publishing work end to end.

Build the separate remote DynApp concept

After the local migration ships, add shell.remote.connect and expose the generic Shell contract over authenticated WSS. Pair Shell installations, bind short-lived credentials to app identity and grants, multiplex calls and events, and make the remote Shell perform an independent permission review.

Risks And Rules

The split only helps if content cannot become an unbounded privileged script runner.

Do not expose raw exec as the core editor API

Raw execution is useful as an escape hatch for trusted editor workflows, but normal app modification should go through typed A2 Code helpers that compose the generic filesystem and process APIs.

Shell owns durability for active work

Provider processes and PTYs must survive content reloads. The Shell owns handles, bounded event replay, leases, and cleanup; A2 Code owns agent/thread state and reconstructs it from its content database plus resumed process events.

Version compatibility

  • Content checks shell capabilities at startup.
  • Shell rejects unknown privileged operations.
  • Feature flags are capability-based, not version-string based.

Security posture

  • All DynApps use the same manifest permission model.
  • A2 Code is powerful because it asks for more capabilities, not because it gets special shell access.
  • Provider secrets stay in Shell storage; package signing stays with the store or release service.
  • The future remote stage must authenticate both devices and independently enforce every grant.

User promise

  • No separate local backend install.
  • Modify works offline for local projects.
  • The first release is local-only; remote DynApps come in a separate later stage.
